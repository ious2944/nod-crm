# Security model

What NOD CRM defends against, how, and — just as importantly — what it does
not.

To *report* a vulnerability, see [SECURITY.md](../SECURITY.md).
To *harden your instance*, see [self-hosting.md](self-hosting.md).

## 1. Threat model

NOD CRM holds business information: who owes what to whom, and by when. Not
regulated data in most jurisdictions, but disclosure would be embarrassing and
loss would be expensive.

### Attack surface

| Entry point | Exposure | Controls |
| --- | --- | --- |
| `GET /login` | public | proxy rate limit, security headers |
| `login` Server Action | public | Zod, Argon2id, dual rate limiting, single generic failure message |
| `GET /`, `/follow-ups` | authenticated | proxy filter + `requireUser()` |
| `createFollowUp` action | authenticated | `requireActor()`, then Zod, then workspace scoping |
| `applyQuickAction` action | authenticated | same, plus object ownership **and** a transition guard |
| `?f=` URL parameter | public | allow-list, silent fallback to `all` |
| `GET /api/health` | loopback | no version, no hostname, no error detail; blocked at the proxy |
| PostgreSQL | **none** | no published port, private Docker network |
| Application port | **loopback** | never `0.0.0.0`, no firewall rule needed |

### What an attacker would want

1. **Read the follow-ups** — needs a valid session; blocked by authentication
   checked in the data access layer.
2. **Guess a password** — Argon2id, application rate limiting, proxy rate
   limiting, optionally Fail2ban.
3. **Enumerate accounts** — one generic failure message, and a constant-cost
   dummy verification when the email is unknown.
4. **Call a Server Action directly** — the most important scenario, and the one
   §3 addresses head-on.
5. **Reach another workspace's data** — see §4.
6. **Reach PostgreSQL** — impossible from outside: no port is published, not
   even on the host's loopback interface.

### Out of model

Host compromise, physical access, npm supply-chain attacks, and a legitimate
user acting maliciously (V0.1 has no privilege separation inside a workspace).

## 2. Authentication

- **Argon2id** with OWASP Password Storage parameters: 19 MiB memory, 2
  iterations, parallelism 1. The salt is generated by the library and embedded
  in the encoded hash.
- **Server-side opaque sessions.** The cookie carries a 256-bit random token;
  the database stores only `HMAC-SHA256(token, AUTH_SECRET)`. A database leak
  alone cannot be turned into a valid cookie.
- **Two expiries.** Absolute (7 days) — the session dies even under continuous
  use. Idle (12 hours) — pushed forward as you browse, but never past the
  absolute deadline. Refreshing writes to the database at most every 5 minutes.
- **Immediate invalidation.** A session that is revoked, expired, or belongs to
  a deactivated user is *deleted* on the next read, not merely rejected.
- **Session fixation prevented.** Any existing session in the browser is
  destroyed before a new one is created at login.
- **Logout destroys server-side** and clears the cookie with matching
  attributes — a `__Host-` cookie cannot be cleared by a `delete()` that omits
  `Secure`, and would otherwise survive logout.

### Why a database session and not a JWT

A JWT cannot be revoked without a server-side list of revoked tokens — at which
point you have a session table with extra steps and worse ergonomics. NOD CRM
needs "log this account out now" to be instantaneous, and it needs deactivating
a user to take effect on the next request. One row and one index does that.

### The cookie

| Attribute | Value | Why |
| --- | --- | --- |
| Name | `__Host-nod_session` in production | the prefix forces `Secure`, `Path=/` and no `Domain`: a subdomain cannot set or overwrite it |
| `HttpOnly` | yes | JavaScript cannot read it, so an XSS cannot exfiltrate it |
| `Secure` | production | never sent over plain HTTP |
| `SameSite` | `Lax` | the CSRF control (see below) |
| `Path` | `/` | required by the `__Host-` prefix |
| Expiry | absolute session deadline | the browser drops it on its own |

### CSRF

`SameSite=Lax` plus Next.js Server Actions. Actions are POST-only, so `Lax`
prevents them being triggered cross-site; Next additionally verifies the
`Origin` against the host for Server Action requests. There is no cross-origin
API to protect: NOD CRM exposes no endpoint other than the health probe.

### Account enumeration

A single message — "email or password incorrect" — for unknown accounts, wrong
passwords and deactivated accounts alike. When the email is unknown, a dummy
Argon2id verification runs anyway, so the response takes the same time as a
real one. Without it, "unknown email" would answer instantly and "wrong
password" after a full hash.

### Password policy

12 characters minimum, at least three character classes, enforced in
`scripts/admin.mjs` — the only code that ever creates a password. Login itself
enforces no complexity rule, only a 256-character ceiling: rejecting a login
for policy reasons would leak the policy, and unbounded input would let anyone
make the server compute Argon2id over a megabyte.

Password reset goes through the CLI. There is no self-service flow, which
means there is no reset-token email path to secure.

## 3. Server-side authorization

**The frontend is not a security boundary.** Anything the interface hides is
still reachable by anyone willing to craft a request.

Every page calls `requireUser()`; every Server Action calls `requireActor()`,
both in `src/lib/auth/dal.ts`, before anything else happens:

```ts
export async function createFollowUp(previous, formData) {
  const workspaceId = await getWorkspaceIdForAction();   // first
  const parsed = createFollowUpSchema.safeParse(…);      // then
```

The order matters. Authenticating before parsing means an unauthenticated
request never influences anything, not even error messages.

`src/proxy.ts` also redirects requests without a session cookie — but that is an
*optimistic* filter that never touches the database, because it runs on every
request including prefetches. A forged cookie passes there and fails in the
data access layer.

A layout is not a boundary either: a child page can render without its parent
layout blocking the flow. `(app)/layout.tsx` calls `requireUser()` for display
convenience; the page and the action check again.

### IDOR / BOLA

Every identifier that arrives from the client is re-checked against the
session's workspace before use:

```ts
const followUp = await prisma.followUp.findFirst({
  where: { id, workspaceId },     // not findUnique({ where: { id } })
});
```

The same applies to `contactId` when creating a follow-up. Guessing a UUID from
another workspace yields "not found", not someone else's data.

### Transition guard

Quick actions check that the requested transition is legal for the item's
current status (`isTransitionAllowed`), then write conditionally:

```ts
await prisma.followUp.updateMany({
  where: { id, workspaceId, status: followUp.status, dueAt: followUp.dueAt },
  data,
});
```

The `where` repeats the exact state read a moment earlier. Two simultaneous
clicks read the same state, but only one `UPDATE` still finds the row in it —
the other updates zero rows and is reported as a conflict. That makes the
transition atomic without an explicit transaction, and it stops a crafted
request from, say, completing an already-abandoned item.

## 4. Workspace isolation

Every business row carries a `workspace_id`, and the workspace comes **from the
session**:

```ts
export async function getWorkspaceIdForAction(): Promise<string> {
  return (await requireActor()).workspaceId;
}
```

There is no code path that lets the browser choose its workspace — no URL
parameter, no form field, no header. A user belongs to exactly one workspace
today; the day they can belong to several, `src/lib/workspace.ts` is the only
file that changes, and the selection will be validated against their
memberships there.

Covered by `tests/integration/workspace-isolation.test.ts`.

## 5. Input validation

Zod schemas at every boundary (`src/lib/*/schemas.ts`). Beyond types:

- **Control characters are stripped**, the NUL byte (`U+0000`) included.
  PostgreSQL rejects it in a text column: without the filter, a title
  containing a NUL turns a Prisma error into a 500 that any authenticated user
  can trigger at will.
- **Invisible Unicode spaces** (U+00A0, U+200B, U+FEFF…) are normalised, so a
  visually empty title cannot pass a `min(1)` check.
- **Dates must round-trip.** `Date.parse` happily accepts `2026-02-31` and
  shifts it to 3 March; the schema requires the parsed date to serialise back
  identically. Bounds of 2000–2100 keep out values that have no business
  meaning and break formatting.
- **UUIDs are pattern-checked** before they reach the database.
- **Length ceilings** on every text field, and on the password.

## 6. Rate limiting

Three layers, from the outside in:

1. **Reverse proxy** — `limit_req`, 10 requests/minute per IP on `/login`.
   Rejects before any application work.
2. **Fail2ban** (optional) — bans repeat offenders at the firewall.
3. **Application** — the last line, in PostgreSQL: 5 failures per account and
   30 per IP over a rolling 15-minute window. Surviving a container restart is
   the reason it is not in memory.

The per-IP threshold is much higher than the per-account one: several people
can share one NAT exit, and a whole office should not be locked out by one
colleague's typos.

### Network identity cannot be forged

Only `X-Real-IP` is trusted, and the proxy overwrites it on every request.
`X-Forwarded-For` is ignored: with `$proxy_add_x_forwarded_for`, the proxy
appends the real address to whatever the client sent, so the first element is
attacker-controlled — a fresh identity per attempt, and per-IP limiting
defeated. If `X-Real-IP` is missing or malformed, the value is `null` and
per-IP limiting is simply skipped; per-account limiting still applies.

IPv6 is aggregated on the first 64 bits, since a subscriber usually gets a
whole /64.

Covered by `tests/integration/adversarial.test.ts`.

## 7. Logging

**Never written:** password, hash, session token, cookie, `Authorization`
header, `DATABASE_URL`.

Authentication events are deliberately impoverished:

```
[auth] event=login.failed account=a***e@example.com src=12ca17b49af2
```

The email is masked and the IP reduced to a 12-character fingerprint: enough to
correlate attempts with each other, not enough to build an address list. Same
in the database — `login_attempts` and `sessions` store fingerprints only.

*Accepted trade-off:* you cannot ban an IP from application logs. That is the
proxy's and Fail2ban's job; they see the real addresses.

Application errors are not returned to the browser. Next shows a trace
identifier and keeps the detail server-side.

## 8. HTTP headers

Emitted by `src/proxy.ts` on every response:

| Header | Value |
| --- | --- |
| `Content-Security-Policy` | `default-src 'self'`, `script-src 'self' 'nonce-<per request>' 'strict-dynamic'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, `upgrade-insecure-requests` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | camera, microphone, geolocation, payment, USB and cohort tracking all denied |
| `X-Frame-Options` | `DENY` (belt and braces alongside `frame-ancestors`) |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `X-Robots-Tag` | `noindex, nofollow` |

The CSP nonce is regenerated per request, and `strict-dynamic` means only
nonce-carrying scripts can load further scripts. `style-src` allows
`'unsafe-inline'` because Next and `next/font` inject unnonced inline styles;
`style-src-attr` remains blocked by default, and `script-src` stays strict —
which is where injection actually hurts.

**HSTS is not set here.** It belongs to the reverse proxy, the only component
that knows the request truly arrived over TLS.

## 9. Secrets

| Secret | Where it lives | Notes |
| --- | --- | --- |
| `AUTH_SECRET` | `.env`, mode 600 | never logged; changing it revokes every session |
| `POSTGRES_PASSWORD` | `.env`, mode 600 | passed to containers as an environment variable, never on a command line |
| Session tokens | the user's cookie | only their HMAC is stored |
| Password hashes | `users.password_hash` | Argon2id, never returned to a client |

`.env` is git-ignored, and `.gitignore` also excludes `*.pem`, `*.key`,
`*.sql.gz` and `/backups`. The `.dockerignore` keeps every `.env*` out of the
build context so nothing lands in an image layer.

In production, `AUTH_SECRET` must exist, be at least 32 characters, and not be
one of the placeholder values shipped in `.env.example`, the Dockerfile or CI —
those are long enough to pass a length check, which made them silently
acceptable before this was enforced.

The check runs at **startup**, in `src/instrumentation.ts`, not on first use.
The secret is only read lazily, when a session token is hashed, so a
misconfigured instance served the login page perfectly and failed with a 500 at
the first login attempt. It now logs one line and exits. Covered by
`tests/unit/auth-secret.test.ts`.

The build-time `AUTH_SECRET` in the Dockerfile is a literal placeholder. The
build needs *a* value because some modules read it at import time; it never
reaches the final image, which copies only `.next`, `node_modules` and a short
list of files.

## 10. Network and isolation

- PostgreSQL publishes **no port at all** — not `5432:5432`, not
  `127.0.0.1:5432:5432`. It is reachable only from the stack's private Docker
  network.
- The application is published on the loopback interface. The reverse proxy is
  the only entry point.
- Containers run with `no-new-privileges`, and the application process runs as
  a non-root user (uid 1001).
- Memory ceilings on both services. Without them a pathological query grows
  until the host kernel kills "a" process, with no guarantee it picks the right
  one. With them, the overrun stays inside NOD CRM's cgroup.
- Log rotation is configured (3 × 10 MB per service), so logs cannot fill the
  disk.

## 11. Dependencies

Ten runtime dependencies. Every one is there because removing it would mean
writing the same thing worse:
Next.js, React, Prisma and its pg adapter, `pg`, `@node-rs/argon2`, Zod,
`server-only`.

`npm audit` is expected to report zero vulnerabilities; one `overrides` entry
(`deepmerge-ts`) exists to keep it that way without downgrading Prisma, and
should be re-evaluated at each Prisma upgrade.

All direct and transitive licenses are permissive or AGPL-compatible (MIT,
Apache-2.0, ISC, BSD, MPL-2.0, LGPL-3.0).

## 12. Residual risks

An honest list of what is *not* covered.

| Risk | Scope | Decision |
| --- | --- | --- |
| No MFA | a stolen password is enough | accepted in V0.1; the model is ready (§13) |
| No roles or permissions | an authenticated user can do anything in their workspace | small teams, single trust level |
| No self-service password reset | goes through the CLI and shell access | deliberate: no email to send, no reset flow to secure |
| Session cookie not bound to an IP | a stolen cookie grants access | binding breaks mobile use for a modest gain |
| No business audit log | you cannot tell who completed which follow-up | on the roadmap |
| No encryption at rest | volume access means data access | belongs to the host, not the application |
| `style-src 'unsafe-inline'` | style injection is possible | a Next.js constraint; `script-src` stays strict |
| Dependency on an npm `overrides` entry | needs watching on upgrade | re-evaluate at each Prisma release |
| Backups sit on the same host | one hardware failure takes both | **fix this**: copy off-site ([backup-restore.md](backup-restore.md)) |
| No pagination | thousands of open follow-ups load at once | acceptable below ~2,000 ([database.md](database.md)) |
| Quick actions require JavaScript | a JS-less browser cannot act on a follow-up | the login screen remains a plain HTML form |
| Fail2ban cannot see failed logins | a rejected password still answers 200 | compensated by application-level limiting |
| Large image (~2.8 GB, full Debian base) | disk, and a wider software surface | slim broke Prisma migrations; revisit with slim + `openssl` if disk gets tight |
| `postgres:16-alpine` is a moving tag | a distant rebuild may pull an untested patch release | acceptable for patch versions; pin by digest if reproducibility becomes critical |
| `C` collation | "Émile" sorts after "Zoé" | fixable in place with an ICU collation ([database.md](database.md)) |

## 13. Ready for, but not built

The model accommodates these without a structural migration:

- **MFA (TOTP)** — add `mfa_secret` and `mfa_enabled` to `users` and an
  intermediate step in the login action. A server-side session can already
  represent a half-authenticated state, which is the part that is usually
  awkward.
- **WebAuthn / passkeys** — a `credentials` table hanging off `users`; the
  session mechanism does not change.
- **Real multi-workspace** — `getWorkspaceIdForPage/Action()` is the single
  point to modify, validating the selection against the user's memberships.

None of the three is implemented in V0.1. Saying so plainly is the point of
this section.
